# 前端性能监控

浏览器采集 Web Vitals，经 CloudWatch Logs 落地，由 ECS 上的清洗服务加工进 PostgreSQL，最后在独立看板上呈现。

## 链路

```
浏览器（页面引入 perf-sdk）
  │  LCP / INP / CLS / FCP / TTFB + 慢资源 + 长任务 + JS 错误 + 自定义打点
  │  会话级采样 → 批量缓冲 → sendBeacon（页面卸载也不丢）
  ▼
API Gateway HTTP API  ──限流 20 rps / 突发 40──▶ 摄取 Lambda（arm64 · 512MB）
                                                    │ 校验 · 截断 · 拍平
                                                    ▼
                                     CloudWatch Logs  /perf/raw（保留 7 天）
                                                    │
                                     每 30 秒 FilterLogEvents 增量拉取
                                                    ▼
                              ECS Fargate 清洗服务（Go · arm64 · 常驻）
                                ├─ 二次校验 / 去噪 / 爬虫过滤 / UA 解析
                                ├─ 按 event_id 去重写入 perf_events
                                ├─ 重算受影响分钟桶 → perf_rollup_1m
                                └─ 推进 perf_checkpoint 水位
                                                    │
                                          同进程暴露查询 API
                                                    │
                        ALB（perf.go-api.jccode.cc）──▶ perf-dashboard 看板
```

## 仓库位置

| 目录 | 内容 |
|------|------|
| `perf-sdk/` | 浏览器 SDK，产物 ESM + IIFE（gzip 约 6 KB，含 web-vitals） |
| `perf-ingest/` | 摄取 Lambda 与 SAM 模板（API Gateway、日志组、告警） |
| `perf-cleaner/` | Go 清洗服务、查询 API、ECS/ALB 的 CloudFormation 模板 |
| `perf-dashboard/` | 独立看板（Vite + React，图表手写 SVG，无第三方图表库） |
| `backend/migrations/003_perf.sql` | 三张表的建表语句 |
| `scripts/perf-deploy.sh` | 一键部署整条链路 |

## 为什么是这套结构

**为什么不让 SDK 直连 CloudWatch Logs**：那需要把 AWS 凭证发到浏览器。摄取端必须是一个不带凭证、只接受写入的公开端点。

**为什么摄取用 Lambda 而不是复用 Go 前门**：摄取与业务请求相互隔离，遥测流量激增不会挤占业务服务。代价是这个账号的 Lambda 并发上限只有 5，所以限流放在 API Gateway 上——挡在函数之前，而不是让函数自己排队。

**为什么轮询而不是订阅过滤器**：订阅过滤器要接 Kinesis Data Stream，按分片小时计费（约 11 美元/月起），不看板的时候也在烧。轮询零额外成本，代价是几十秒延迟——对性能看板完全够用。

**为什么清洗服务同时提供查询 API**：它已经握着这个库唯一的热连接池，而看板的读量相对上报量是零头。多起一个服务只会多一份部署和一份故障面。

**为什么 Web Vitals 用 Google 的 web-vitals 库而不自己写**：这几个指标的测量规则不是能查一次就固定下来的常识，它跟着浏览器行为一直在变，而且写错的方向往往是一致的——指标看起来比实际更差，会让人去优化并不存在的问题。库处理了几件手写版本很容易漏掉的事：

- **LCP 在首次交互时终止**。用户点开的大图不算最大内容绘制，只在页面隐藏时定稿会把它算进去
- **INP 的分位索引用 `performance.interactionCount`**，包含快于观察阈值的交互。只统计观察到的交互会让索引偏小、INP 偏高
- **bfcache 恢复后重新测量**。否则用户点返回回到页面，这第二次浏览完全没有数据
- **预渲染页面按 `activationStart` 校正**，不然 LCP/FCP/TTFB 全部偏大

代价是约 2.9 KB gzip。`vitals.ts` 只是适配层，把库的 `Metric` 映射成上报事件；采样、批量、传输、慢资源与错误采集都还是自己的。评级也直接采用库给的 `rating`——本地只保留 RESOURCE 和 LONGTASK 的阈值，避免两份阈值各自漂移。

**为什么百分位从明细重算而不是合并**：百分位不能加权合并，误差恰好集中在最该看的慢尾上。保留期内的查询一律从 `perf_events` 精确计算；超出保留期才退回按样本数加权合并 `perf_rollup_1m`，此时响应里 `approximate: true`，看板上会明确标注。

## 数据契约

SDK 发出的批量载荷：

```json
{
  "v": 1,
  "sdk": "perf-sdk@1.0.0",
  "site": "zuoye-frontend",
  "session": "01J...",
  "page": "/users/:id",
  "ua": "Mozilla/5.0 ...",
  "conn": "4g",
  "events": [
    { "id": "01J...", "name": "LCP", "value": 1834.2, "rating": "good", "at": 1785000000000,
      "attrs": { "element": "img#hero" } }
  ]
}
```

摄取 Lambda 把它拍平成每事件一行 JSON 写入日志组：载荷级字段并进每个事件，清洗侧读一行就是一条完整记录，不必跨日志条目重组批次。

`v` 是双方的版本契约。不认识的版本一律拒绝，不做猜测。

指标取值：`LCP` `FCP` `CLS` `INP` `TTFB` `RESOURCE` `LONGTASK` `CUSTOM` `ERROR`。除 CLS（无量纲得分）和 ERROR（次数）外单位均为毫秒。

## 清洗规则

| 规则 | 原因 |
|------|------|
| schema 版本必须匹配 | 日志组是独立边界，可能收到旧版本或重放的数据 |
| 每指标独立数值上限（LCP 120s、CLS 10 …） | 超过的不是"慢"，是坏测量，会把百分位拖到没有真实用户的位置 |
| 时间戳必须落在保留窗口内 | 一个月前的重放流会改写早已正确的聚合 |
| 爬虫 UA 直接丢弃 | 合成流量测的是爬虫的机器，且普遍更快，留着会让所有页面显得比实际好 |
| 剥离 NUL 与控制字符，按 rune 边界截断 | text 和 jsonb 都拒收 U+0000，一个恶意字符串就能让整批插入失败 |
| 评级缺失或非法时按数值重算 | 评级是派生值，重建的代价远小于丢样本 |
| 嵌套属性直接丢弃 | 这是载荷里唯一大小没有自然上界的部分 |

丢弃按原因分类计数并打进日志——"丢了 300 条"没有信息量，"300 条爬虫"和"300 条未知指标"要采取的行动完全相反。

## 至少一次与幂等

轮询每轮都回退 2 分钟重读，因为日志投递并不严格按时间戳有序，窗口末尾几秒还可能补进事件。重复因此是常态而非异常：

- `perf_events` 以 `event_id` 为主键，`ON CONFLICT DO NOTHING`
- 聚合永远按分钟桶整体重算，而不是增量累加，所以重放收敛到同一结果
- 先重算聚合再推进水位。中间崩溃只会导致下一轮重复做一遍，不会丢数据

## 查询 API

服务在 `https://perf.go-api.jccode.cc`：

| 路径 | 说明 |
|------|------|
| `GET /health` | 存活检查（含数据库连通性），ALB 用它做健康检查 |
| `GET /api/sites` | 近期有上报的站点 |
| `GET /api/pages?site=` | 站点下按流量排序的页面 |
| `GET /api/summary?site=&range=24h&page=` | 各指标的 p50/p75/p95 与评级分布 |
| `GET /api/timeseries?site=&metric=LCP&range=24h&page=` | 时间序列，桶宽按跨度自动选择 |
| `GET /api/breakdown?site=&metric=LCP&range=24h&limit=10` | 按页面分布，按流量排序 |

`range` 支持 `30m` `6h` `7d` 这类写法（Go 原生不认 `d`，这里额外支持），也可以用 `from`/`to` 传 RFC3339 绝对时间。

## 本地开发

看板通过 `file:` 依赖引用 SDK，而 npm 只是把那个目录链接过来、不会替它构建，所以 **SDK 要先构建一次**：

```bash
cd perf-sdk       && npm ci && npm run build
cd ../perf-dashboard && npm ci && npm run dev
```

其余组件互相独立，直接 `npm ci` 或 `go test ./...` 即可。清洗服务的 `store` 包需要真实 PostgreSQL：

```bash
cd backend && docker compose up -d && npm run migrate
cd ../perf-cleaner && TEST_DATABASE_URL=postgres://appuser:localdevpassword@localhost:5432/github_users go test ./...
```

不设 `TEST_DATABASE_URL` 时这些用例自动跳过，`go test ./...` 在没有数据库的机器上依然是绿的。

## 部署

```bash
cp perf-cleaner/deploy.env.example perf-cleaner/deploy.env   # 填 DATABASE_URL
./scripts/perf-deploy.sh
```

脚本按顺序完成：读现有网络配置 → 部署摄取栈 → 跑迁移 → 构建推送 ARM64 镜像 → 部署 ECS 栈 → 构建前端产物。网络参数（子网、安全组、ALB 监听器）都从现有 Go 服务上动态读取，不写死，避免两处配置漂移。

CI（`.github/workflows/perf.yml`）跑的是同一个脚本，只是把配置换成环境变量，并在之后做端到端冒烟：发一条合法上报应得 204，发一条畸形的应得 400，然后轮询查询 API 直到那条数据出现在聚合里。看板由 `cloudflare/wrangler-action` 发布到 Pages 项目 `zuoye-perf-dashboard`，前面一步 `pages project create` 带 `continue-on-error`，所以首次推送会自动建项目、后续重复执行也不会失败。

CI 部署有两处和本地不同，都不是可选项：

**迁移跳过（`SKIP_MIGRATION=1`）**。RDS 不对公网开放，GitHub runner 没有进 VPC 的路由。**schema 变更必须先人工经跳板机迁移，再推触发部署**——和 collector 的做法一致。忘了这一步的话，清洗服务会部署成功然后每一轮轮询都失败。

**部署角色的 IAM 权限按栈前缀限定**。`zuoye-github-actions-deploy` 挂的 `PowerUserAccess` 明确排除 IAM，实际权限来自内联策略 `iam-for-sam`，原本只覆盖 `zuoye-collector-*`。这两个栈要自建角色（摄取 Lambda 的执行角色、清洗服务的 TaskRole），还要把现有的 `zuoye-ecs-execution-role` 传给 ECS，所以策略补了：

| 新增 | 为什么 |
|---|---|
| `zuoye-perf-*` 加入 `IamScopedToSam` 的资源列表 | 两个栈生成的角色名都在这个前缀下 |
| 新语句 `PassSharedEcsExecutionRole` | 注册 ECS 任务定义需要 `iam:PassRole` 到那个共享执行角色，它不在任何 `zuoye-perf-*` 前缀里 |

边界没有放宽到通配：`admin-backdoor`、`zuoye-go-task-role` 这类目标仍是 `implicitDeny`，角色也删不掉自己。

## 页面接入

```html
<script src="/perf-sdk.iife.js"></script>
<script>
  PerfSDK.init({
    endpoint: "https://<api-id>.execute-api.us-east-2.amazonaws.com/v1/collect",
    site: "zuoye-frontend",
    sampleRate: 1,
  });
</script>
```

打自定义点：

```js
const perf = PerfSDK.init({ ... });
perf.mark("search", performance.now() - started, { query: username });
```

采样是**会话级**而非事件级：半个会话有 LCP 没有 TTFB，会让任何按会话的比较失去意义。

## 成本与限制

- CloudWatch Logs 保留 7 天，明细表同样保留 7 天（分钟聚合永久保留）
- 清洗服务 1 个 Fargate 任务（0.25 vCPU / 0.5 GB）
- 摄取 Lambda 512 MB——这个账号的硬上限，见 [学习笔记](学习笔记.md)
- API Gateway 限流 20 rps：账号 Lambda 并发只有 5，必须挡在函数之前
- 清洗服务固定 1 个实例。多开会重复轮询同一日志组，`event_id` 让它无害，但不是免费的
