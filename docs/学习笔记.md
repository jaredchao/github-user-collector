## 1. 架构总览

```
                    Cloudflare Pages（前端，全球 CDN）
                              │
                              │ HTTPS + CORS 预检
                              ▼
                      API Gateway（HTTP API，公网唯一入口）
                              │
    ┌─────────────────────────┼──────────────────────────────────┐
    │  VPC 10.0.0.0/16        ▼                                  │
    │                                                            │
    │  公有子网 10.0.0.0/24 (2a) · 10.0.1.0/24 (2b)              │
    │      └── NAT Gateway ──► Internet Gateway ──► 公网         │
    │                ▲                                            │
    │                │ 出站（仅出不进）                           │
    │                                                            │
    │  私有子网 10.0.10.0/24 (2a) · 10.0.11.0/24 (2b)            │
    │      ├── Lambda（Hono）                                    │
    │      │      ├──► GitHub API（经 NAT）                      │
    │      │      └──► RDS :5432（TLS 1.3）                      │
    │      ├── RDS PostgreSQL                                    │
    │      └── 跳板机（无公网 IP）                               │
    │                ▲                                            │
    └────────────────┼────────────────────────────────────────────┘
                     │ SSM 加密隧道
                你的笔记本（跑数据库迁移、排障）
```

**核心不变式**：Lambda、RDS、跳板机**都没有公网 IP**，也**没有任何入站端口对公网开放**。所有出站流量经 NAT，所有入站访问只能从 API Gateway 进。

### 请求的完整生命周期

用户在前端输入 `torvalds` 点搜索：

1. 浏览器先发 `OPTIONS` 预检（跨域），API Gateway → Lambda → Hono 的 CORS 中间件返回 `204` + 允许头
2. 浏览器再发真正的 `POST /users`，body 是 `{"username":"torvalds"}`
3. API Gateway 把请求包成 event，调用 Lambda（**这一步走 AWS 内部服务调用，不经过 VPC 网络**）
4. Lambda 在私有子网里运行，`fetch` GitHub API → 私有路由表 `0.0.0.0/0` → NAT Gateway → IGW → 公网
5. 拿到 JSON，`INSERT ... ON CONFLICT (username) DO UPDATE` 写 RDS，走 VPC 内网 + TLS 1.3
6. 返回 `201` + 用户 JSON，CORS 头由 Hono 附上
7. 前端渲染卡片

第 3 步是个容易误解的地方：**API Gateway 调用 Lambda 不受安全组管辖**。安全组管的是 Lambda 的网卡（ENI），而 API Gateway 是通过 Lambda 服务的控制面调用函数的。所以 `sg-lambda` 的入站规则可以是空的。

## 3. 账号与权限

### AWS 免费计划（新版）

不是老的"12 个月免费套餐"，而是**赠金制**：

- 开户送 **$200 赠金**，有效期 6 个月
- 期间所有消费先从赠金扣，**不刷信用卡**
- 到期条件：赠金用完 **或** 到期日，二者先到为准

```python
r = c.get_account_plan_state()

# accountPlanType: FREE
# accountPlanRemainingCredits: {"amount": 198.72, "unit": "USD"}

```

查账单明细：

```bash
aws ce get-cost-and-usage \
  --time-period Start=2026-07-01,End=2026-08-01 \
  --granularity MONTHLY --metrics UnblendedCost \
  --group-by Type=DIMENSION,Key=SERVICE
```

按记录类型分组（能看出赠金抵扣了多少）：

```bash
aws ce get-cost-and-usage ... --group-by Type=DIMENSION,Key=RECORD_TYPE
```

### IAM 策略选型

| 策略 | 能做什么 | 适用 |
|------|---------|------|
| `AdministratorAccess` | 一切，含 IAM 管理 | 图省事，风险最大 |
| `PowerUserAccess` | 几乎一切，**但禁止所有 IAM 写操作** | 日常推荐 |
| `ReadOnlyAccess` | 只读 | 纯浏览学习 |

**PowerUserAccess 的真面目**（很多教程说错）：

```json
{ "Effect": "Allow", "NotAction": ["iam:*", "organizations:*", "account:*"], "Resource": "*" }
```

`NotAction: iam:*` 意味着**连 `iam:ListAttachedUserPolicies` 都不行**——你甚至查不到自己有哪些策略。它只额外放行 `iam:CreateServiceLinkedRole` 等极少数操作。

**这直接导致：SAM 部署会失败**，因为 SAM 要 `iam:CreateRole` 来创建 Lambda 执行角色。这是本项目遇到的第一个架构级阻碍，见 [坑 #14](#13-坑总表)。

### 服务专属策略的命名规律

猜就能猜对大半：`Amazon<服务>FullAccess` / `Amazon<服务>ReadOnlyAccess`。

| 服务 | 策略名 | 备注 |
|------|--------|------|
| VPC | `AmazonVPCFullAccess` | |
| Lambda | `AWSLambda_FullAccess` | 注意是下划线 |
| S3 | `AmazonS3FullAccess` | |
| EC2 | `AmazonEC2FullAccess` | 已含大部分 VPC 操作 |
| API Gateway | `AmazonAPIGatewayAdministrator` | 不叫 FullAccess |
| CloudWatch 日志 | `CloudWatchLogsFullAccess` | 调试必备 |

一个用户最多直接附加 10 个托管策略。

## 4. 网络层：VPC 与子网

### 创建 VPC 时必须做的一件事

控制台 → VPC → Create VPC → **选「VPC only」，不要选「VPC and more」**。

后者是个向导，一键把子网、IGW、NAT、路由表全建好。真实工作里好用，但学习时它把你要理解的东西全藏起来了。

建完之后：**Actions → Edit VPC settings → 勾选 Enable DNS hostnames**。

> **为什么必须开**：RDS 给的端点是域名（`database-1.xxx.rds.amazonaws.com`）。VPC 没开 DNS hostnames 时，Lambda 在 VPC 内解析这个域名会失败，报的错是**连接超时**，而不是"DNS 解析失败"。你会往安全组、路由表方向排查很久，想不到是这个开关。
>
> 用向导建的 VPC 默认开着这个开关，手动建的默认关着——所以看别人的教程"没提到要开"，是因为他们用了向导。

验证：

```bash
aws ec2 describe-vpc-attribute --vpc-id <vpc-id> --attribute enableDnsHostnames
aws ec2 describe-vpc-attribute --vpc-id <vpc-id> --attribute enableDnsSupport
# 两个都要是 true
```

### 子网规划

| 子网 | CIDR | 可用区 |
|------|------|--------|
| public-a | `10.0.0.0/24` | us-east-2a |
| public-b | `10.0.1.0/24` | us-east-2b |
| private-a | `10.0.10.0/24` | us-east-2a |
| private-b | `10.0.11.0/24` | us-east-2b |

**为什么公有从 `.0`/`.1` 开始，私有跳到 `.10`/`.11`？**
中间留出 `10.0.2.x` ~ `10.0.9.x` 的空隙。将来加公有子网往 `10.0.2.0/24` 加，加私有往 `10.0.12.0/24` 加，两组永不撞车，看 IP 第三段就知道属于哪类。

**为什么每类都要两个、跨不同 AZ？**

1. **RDS 的硬性要求**：创建 RDS 前必须建「DB 子网组」，而 DB 子网组**强制覆盖至少 2 个可用区**，哪怕你只建单 AZ 实例。不知道这条的话，走到 RDS 那步会被卡住。
2. 可用区是物理隔离的机房，跨 AZ 是高可用的基础。

**`/24` 有多少 IP？** 256 个，AWS 保留 5 个（网络地址、VPC 路由器、DNS、预留、广播），实际可用 251。

### 子网本身没有「公有/私有」属性

这是最反直觉的一点。

子网叫 `public-a` 只是个名字标签。**它是公有还是私有，完全取决于它关联的路由表里 `0.0.0.0/0` 指向谁**：

- 指向 Internet Gateway → 公有子网（双向通公网）
- 指向 NAT Gateway → 私有子网（只能出，不能进）
- 没有 `0.0.0.0/0` 路由 → 完全隔离

创建子网时**不需要也不能**设置这个属性。

### 坑：可用区不会自动切换

控制台上「一次创建多个子网」时，点「Add new subnet」加的新子网，**可用区默认还是上一个的**，必须手动改。本项目第一次建时 4 个子网全在 `us-east-2a`，直到验证时才发现。

子网创建后**不能改可用区**，只能删掉重建（空子网删除零成本）。

验证：

```bash
aws ec2 describe-subnets --filters "Name=vpc-id,Values=<vpc-id>" \
  --query 'Subnets[].[Tags[?Key==`Name`]|[0].Value,CidrBlock,AvailabilityZone]' --output table
```

## 5. 网络层：网关与路由

顺序很重要：**IGW → NAT → 路由表**。NAT 建在公有子网里，而公有子网要能上网就得先有 IGW。

### 5a. Internet Gateway

创建后状态是 **Detached**，必须 **Actions → Attach to VPC**。

IGW 是 VPC 通往公网的「门」。挂上了不代表流量会走它——还得有路由指过去。

### 5b. NAT Gateway

| 字段 | 值 |
|------|-----|
| Subnet | **公有子网**（`zuoye-public-a`） |
| Connectivity type | Public |
| Elastic IP | 点 Allocate Elastic IP 自动分配 |

创建后状态 `Pending`，**要等 2~3 分钟变 `Available`**，否则下一步的路由表里选不到它。

**NAT 放公有子网，服务的却是私有子网** —— 这是最容易绕晕的点。

NAT 的工作是替私有子网的机器代理访问外网：收到私有子网的请求 → 换成自己的公网 IP 发出去 → 收到响应再转回去。既然它自己要能上公网，就必须待在一个能走 IGW 的子网里。

**为什么外面进不来**：NAT 只对「从内部发起的连接」做地址转换，不接受从公网主动发起的连接。这就是私有子网「能出不能进」的由来。

### 5c. 两张路由表

```
zuoye-rtb-public                    zuoye-rtb-private
├─ 10.0.0.0/16 → local              ├─ 10.0.0.0/16 → local
└─ 0.0.0.0/0   → igw-xxx            └─ 0.0.0.0/0   → nat-xxx
关联: public-a, public-b            关联: private-a, private-b
```

**两张表的唯一区别就是那条 `0.0.0.0/0` 指向谁。**

`10.0.0.0/16 → local` 是 AWS 自动加的，保证 VPC 内部互通，删不掉。

### 主路由表：不要碰它

每个 VPC 创建时自带一张 **main route table**，只有 `local` 一条路由。任何**没有显式关联路由表**的子网都默认走这张表。

我们建两张自己的表，显式关联到对应子网，**不动主表**。因为主表是「兜底」——如果把它改成能上公网，那么任何忘了关联路由表的新子网都会**意外变成公有子网**。

验证：

```bash
aws ec2 describe-route-tables --filters "Name=vpc-id,Values=<vpc-id>" --output json | python3 -c "
import json, sys
for rt in json.load(sys.stdin)['RouteTables']:
    name = next((t['Value'] for t in rt.get('Tags', []) if t['Key'] == 'Name'), '(主表)')
    main = any(a.get('Main') for a in rt.get('Associations', []))
    print(f\"[{name}]{' MAIN' if main else ''}\")
    for r in rt['Routes']:
        tgt = r.get('GatewayId') or r.get('NatGatewayId') or '?'
        print(f\"  {r.get('DestinationCidrBlock','?'):<16} -> {tgt}\")
    subs = [a['SubnetId'] for a in rt.get('Associations', []) if a.get('SubnetId')]
    print(f'  关联: {subs or \"(无)\"}')
"
```

### 高可用的取舍

生产环境为了高可用会**每个 AZ 建一个 NAT + 一张私有路由表**，一个 AZ 挂了另一个还活着。代价是 NAT 费用翻倍（每个约 $33/月）。

本项目一个 NAT 服务两个私有子网，跨 AZ 会产生少量数据传输费，可忽略。

## 6. 网络层：安全组

**路由表决定流量能不能到达，安全组决定到达后放不放行。** 两层独立机制，都对才通。

### 三个安全组

| 安全组 | 入站规则 | 出站规则 |
|--------|---------|---------|
| `zuoye-sg-lambda` | **无** | 全部允许 |
| `zuoye-sg-bastion` | **无** | 全部允许 |
| `zuoye-sg-rds` | `5432` ← `sg-lambda`、`sg-bastion` | 全部允许 |

**创建顺序**：先建 lambda 和 bastion，再建 rds（rds 的规则要引用前两个）。

### Lambda 入站为空是对的

Lambda 不接受任何主动连入的连接。API Gateway 调用 Lambda 走的是 **AWS 内部服务调用，不经过 VPC 网络，不受安全组管辖**。Lambda 只需要**出站**能力：访问 RDS（`10.0.x.x`）和 GitHub（经 NAT 出公网）。

### 跳板机入站为空是重点

传统跳板机要开 `22` 端口收 SSH。我们不开——**SSM Session Manager 是跳板机上的 agent 主动向外连 AWS**，是出站连接。所以入站可以彻底关死。

这就是 SSM 比 SSH 跳板机安全得多的根本原因：**没有任何端口暴露给外界扫描**。

### 按安全组授权，而不是按 IP 段

`sg-rds` 的 Source 那一栏要选 **Custom → 搜索安全组名字**，填对了会显示成 `sg-xxxxx` 而不是一个 CIDR。

你也可以写 `10.0.10.0/24, 10.0.11.0/24`（两个私有子网网段）达到类似效果，但**按安全组引用更好**：

1. **Lambda 的 IP 是漂移的**。Lambda 在 VPC 里的 ENI 由 AWS 动态分配，扩容时占用子网里任意空闲 IP。按网段放行等于把整个子网都放行了——将来往这个子网放任何东西，它都自动获得了访问数据库的权限。
2. **这是「身份」而非「位置」**。规则读起来是：「凡是挂了 `sg-lambda` 的资源，允许连我的 5432」。跟它在哪个子网、什么 IP 无关。把 Lambda 挪到别的子网，规则依然生效。
3. **意图自解释**。看到 `sg-lambda` 立刻知道这是给 Lambda 开的；看到 `10.0.10.0/24` 则要反查这个网段是什么。

### 安全组是有状态的

允许了入站请求，对应的**响应包自动放行**，不用再配出站规则。这点和传统防火墙（网络 ACL）不同——网络 ACL 是无状态的，得两个方向都配。

### VPC 自带的 default 安全组

删不掉，规则是「允许自身成员互通」。**只要不把任何资源挂到它上面就行**。创建 RDS 时控制台默认会带上它，记得移除。

验证：

```bash
aws ec2 describe-security-groups --filters "Name=vpc-id,Values=<vpc-id>" --output json | python3 -c "
import json, sys
gs = json.load(sys.stdin)['SecurityGroups']
byid = {g['GroupId']: g['GroupName'] for g in gs}
for g in gs:
    print(f\"[{g['GroupName']}] {g['GroupId']}\")
    for p in g['IpPermissions'] or []:
        for r in p.get('IpRanges', []): print(f\"  入站 {p['IpProtocol']}/{p.get('FromPort')} <- CIDR {r['CidrIp']}\")
        for r in p.get('UserIdGroupPairs', []): print(f\"  入站 {p['IpProtocol']}/{p.get('FromPort')} <- SG {byid.get(r['GroupId'])}\")
    if not g['IpPermissions']: print('  入站 (无)')
"
```

## 7. 数据库：RDS

### 先建 DB 子网组

RDS 控制台 → Subnet groups → Create DB subnet group

- VPC：`zuoye-vpc`
- Availability Zones：勾选 `us-east-2a` 和 `us-east-2b`
- Subnets：**只勾私有的两个**（`10.0.10.0/24`、`10.0.11.0/24`）

页面会把 4 个子网都列出来。勾错成公有子网的话，数据库就坐在能通公网的子网里了——虽然还有安全组挡着，但丢掉了纵深防御的第一道防线。

**这一步会强制你选至少 2 个 AZ**，这就是第 4 章说的那个硬性要求。

### 创建实例的关键选项

| 字段 | 值 | 说明 |
|------|-----|------|
| 创建方式 | **Standard create** | 不要 Easy create，它替你做太多决定 |
| Engine | PostgreSQL | |
| Templates | **Free tier** | 自动锁定单 AZ、最便宜规格 |
| Credentials | Secrets Manager 或自管密码 | 见下方讨论 |
| Instance class | `db.t4g.micro` | |
| **Storage autoscaling** | **取消勾选** | 防止意外扩容烧赠金 |
| Compute resource | Don't connect to EC2 | |
| DB subnet group | `zuoye-db-subnet-group` | |
| **Public access** | **No** | 绝不能选 Yes |
| VPC security group | Choose existing → `zuoye-sg-rds`，**移除 default** | |
| **Initial database name** | **`github_users`** | 藏在折叠的 Additional configuration 里 |
| Enhanced monitoring | 取消勾选 | 省钱 |
| **Deletion protection** | **取消勾选** | 否则最后删不掉 |

### 坑：Initial database name 不填会怎样

RDS 只给你一个空实例，里面**没有名叫 `github_users` 的数据库**。你的 `DATABASE_URL` 会连接失败。

这个字段藏在折叠的「Additional configuration」里，是最常见的遗漏。

### 坑：RDS 强制 SSL

PostgreSQL 15+ 的默认参数组里 `rds.force_ssl = 1`。明文连接会被拒，报错是：

```
error: no pg_hba.conf entry for host "10.0.10.196", user "postgres",
       database "github_users", no encryption
```

**关键线索是末尾的 `no encryption`**，但错误信息主体说的是「没有匹配的 pg_hba 条目」，很容易往权限、白名单方向排查半天。

确认参数：

```bash
PG=$(aws rds describe-db-instances --db-instance-identifier database-1 \
  --query 'DBInstances[0].DBParameterGroups[0].DBParameterGroupName' --output text)
aws rds describe-db-parameters --db-parameter-group-name "$PG" \
  --query "Parameters[?ParameterName=='rds.force_ssl'].[ParameterName,ParameterValue,Source]" --output table
# rds.force_ssl | 1 | system
```

**不要关掉它。** 数据库连接本来就该加密。解决办法是在连接串里加 `sslmode`。

### sslmode 该用哪个

| 值 | 加密 | 校验证书 | 校验主机名 |
|----|------|---------|-----------|
| `disable` | ✗ | | |
| `require` | ✓ | ✗（node-postgres 会用系统 CA 校验，RDS 证书不在里面 → 失败） | |
| `no-verify` | ✓ | ✗ | ✗ |
| `verify-ca` | ✓ | ✓ | ✗ |
| `verify-full` | ✓ | ✓ | ✓ |

**经 SSM 隧道连接时必须用 `no-verify`**：隧道的本地端是 `localhost`，而 RDS 证书上写的域名是 `database-1.xxx.rds.amazonaws.com`，主机名对不上，严格校验必然失败。

**Lambda 在 VPC 内直连真实端点**，主机名匹配，理论上应该用 `verify-full` + 下载 AWS 的 RDS CA 证书包。本项目为简化仍用 `no-verify`，这是**已知的妥协**。

验证连接确实加密：

```sql
SELECT ssl, version FROM pg_stat_ssl WHERE pid = pg_backend_pid();
-- t | TLSv1.3
```

这是硬证据——不是「配置里写了 SSL」，而是「这条实际连接确实在 TLS 1.3 上跑」。

### 关于密码存哪

| 方案 | 成本 | 安全性 |
|------|------|--------|
| Secrets Manager | $0.40/密钥/月 | Lambda 用 IAM 权限读，永不落盘 |
| Lambda 环境变量 | 免费 | **控制台明文可见** |

本项目为省钱用了环境变量。作业里诚实的表述是：

> 知道正确做法是 Secrets Manager，出于成本考虑本次用环境变量，这是一个有意识的权衡。

比装作没这回事强得多。

## 8. 跳板机与 SSM 隧道

### 为什么需要跳板机

RDS 在私有子网、`Public access = No`、没有公网 IP。**你的笔记本根本路由不到它**。但你需要连上去建表、排查问题。

传统做法是在公有子网放一台 SSH 跳板机，开 22 端口。我们不这么干。

### 为什么跳板机放私有子网

SSM Session Manager 的工作原理是**实例上的 agent 主动向外连接 AWS 的 SSM 服务**，而不是你从外面连进去。

所以跳板机：
- 放**私有子网**
- **没有公网 IP**
- 安全组**入站规则为空**
- 走 NAT 出去被 SSM 管理

放公有子网只是白白多暴露一个攻击面。

### 创建步骤

**先建 IAM 角色**：IAM → Roles → Create role → AWS service → EC2 → 附加 **`AmazonSSMManagedInstanceCore`** → 命名 `zuoye-bastion-role`。

**再建 EC2**：

| 字段 | 值 |
|------|-----|
| AMI | **Amazon Linux 2023**（预装 SSM agent） |
| Instance type | `t4g.nano` 或 `t3.micro` |
| Key pair | **Proceed without a key pair** |
| Subnet | `zuoye-private-a` |
| Auto-assign public IP | **Disable** |
| Security group | `zuoye-sg-bastion` |
| **IAM instance profile** | **`zuoye-bastion-role`** ← 藏在 Advanced details 里 |

### 坑：IAM instance profile 漏了

这一项在折叠的「Advanced details」里，极易漏。漏了的话实例能正常启动，但**SSM 里永远看不到它**，显示不出可连接的实例，且没有任何明显报错。

### 坑：必须先有 NAT

跳板机在私有子网，SSM agent 要能访问 SSM 服务端点才能注册。这条路径是：

```
跳板机 (10.0.10.x) → 私有路由表 0.0.0.0/0 → NAT Gateway → IGW → AWS SSM 服务
```

**NAT 没通，跳板机就永远显示离线。** 所以顺序不能乱。

反过来说，**跳板机能被 SSM 管理，就证明你的 NAT 和私有路由表配对了**。这是检验网络配置最好的探针。

```bash
aws ssm describe-instance-information \
  --query 'InstanceInformationList[].[InstanceId,PingStatus,AgentVersion]' --output table
# i-054f0ce87b8bea714 | Online | 3.3.4624.0
```

`Online` 就是通行证。

### 坑：session-manager-plugin 要单独装

AWS CLI **自己不会做端口转发**，它只是个「谈判者」。真正干活的是一个独立的二进制。

```bash
brew install --cask session-manager-plugin
session-manager-plugin --version   # 1.2.835.0
```

没装的话 `aws ssm start-session` 报 `SessionManagerPlugin is not found`。

### 开隧道

```bash
aws ssm start-session \
  --target i-054f0ce87b8bea714 \
  --document-name AWS-StartPortForwardingSessionToRemoteHost \
  --parameters '{"host":["database-1.c3a80c2swc1v.us-east-2.rds.amazonaws.com"],"portNumber":["5432"],"localPortNumber":["5433"]}'
```

三个参数的分工：

| 参数 | 值 | 谁来解释 |
|------|-----|---------|
| `host` | RDS 端点域名 | **跳板机**（在 VPC 内解析并连接） |
| `portNumber` | `5432` | 跳板机 |
| `localPortNumber` | `5433` | **本地插件**（在你笔记本开这个口） |

本地用 5433 是因为 5432 通常被本机 Docker 的 PostgreSQL 占了，两者可以并存：一个是本地开发库，一个是云上 RDS。

命令会一直挂在前台，打印 `Port 5433 opened for sessionId ...`。**这个终端窗口就不能干别的了**，另开一个去连数据库。`Ctrl+C` 关闭。

### 隧道到底是什么

进程树：

```
zsh
 └─ aws ssm start-session (Python)      ← 只负责跟 AWS 谈判
     └─ session-manager-plugin (Go)     ← 真正监听 5433 的是它
```

**`aws ssm start-session` 做前半段**：
1. 用 `~/.aws/credentials` 调 AWS API `StartSession`
2. AWS 返回 `SessionId`、`TokenValue`（临时令牌）、`StreamUrl`（WebSocket 地址）
3. exec 出 `session-manager-plugin`，**把这三样当命令行参数传过去**

**`session-manager-plugin` 做后半段**：
1. 拿 `TokenValue` 连那个 WebSocket
2. 在 `127.0.0.1:5433` 开 TCP 监听
3. 谁连上来，就把字节流封包塞进 WebSocket；回来的数据写回 TCP

> 副作用：`ps aux` 能看到明文的 `TokenValue`（因为它是命令行参数）。它是这条会话的临时令牌，会话结束即失效，危害有限——但这说明**命令行参数在 Unix 上是公开的**，别用这种方式传长期密钥。

### 完整链路

```
你的程序 ──► 127.0.0.1:5433
                  │  session-manager-plugin 监听在这里
                  ▼
             (可能经本机代理，如 127.0.0.1:7890)
                  │  加密 WebSocket
                  ▼
             AWS SSM 服务
                  ▼
             跳板机 10.0.10.196
                  │  它在 VPC 内部发起普通 TCP 连接
                  ▼
             RDS 10.0.11.228:5432  [TLS 1.3]
```

### 最有说服力的验证

```sql
SELECT inet_client_addr(), inet_server_addr();
-- 10.0.10.196/32  |  10.0.11.228/32
```

你的 `pg` 驱动连的是 `localhost:5433`，但**数据库看到的客户端 IP 是跳板机**。数据库压根不知道你的笔记本存在。

**你的程序以为数据库在本机 5433，数据库以为客户端是跳板机——两边都被骗了，这正是端口转发的定义。**

### 观察隧道的命令

| 想知道什么 | 命令 |
|-----------|------|
| 隧道开着吗 | `lsof -nP -iTCP:5433 -sTCP:LISTEN` |
| 绑在哪个地址 | 同上，看是 `127.0.0.1:5433` 还是 `0.0.0.0:5433` |
| 进程树 | `ps -o pid,ppid,command -p <pid>` |
| AWS 侧活跃会话 | `aws ssm describe-sessions --state Active` |
| **历史会话（审计）** | `aws ssm describe-sessions --state History` |
| 端口通不通 | `nc -zv localhost 5433` |
| 数据库怎么看我 | `SELECT inet_client_addr()` |
| 跳板机在线吗 | `aws ssm describe-instance-information` |

**绑定地址要是 `127.0.0.1` 而不是 `0.0.0.0`**。绑到 `0.0.0.0` 的话，同一局域网（比如咖啡厅 WiFi）里的任何人都能通过你的隧道直连生产数据库。SSM 插件默认只绑回环地址。

### SSM 相对 SSH 的核心优势：审计

```bash
aws ssm describe-sessions --state History
# 谁、什么时候连的、连了多久、连的哪台机器、什么类型的操作
```

传统 SSH 跳板机做不到——登录记录只在那台机器的 `/var/log/auth.log` 里，攻击者拿到 root 就能抹掉。**SSM 的记录在 AWS 控制平面，跳板机被完全攻陷也改不了。**

### 关闭隧道

```bash
# 前台运行时
Ctrl+C

# 后台运行时
kill $(lsof -nP -tiTCP:5433 -sTCP:LISTEN)

# 从 AWS 侧强制断开
aws ssm terminate-session --session-id <会话ID>
```

## 9. 应用代码的关键设计

### 先本地跑通，再上云

**别同时调试两个未知数。**

如果先把整套 VPC/RDS/Lambda/网关搭好再把代码丢上去，一旦调不通，你分不清是**代码逻辑错了**还是**网络/权限没配对**。两个变量纠缠在一起，排错要命。

反过来，代码已在本地验证过「确实能拉 GitHub + 确实能写库」，那么部署后出问题，**问题一定出在基础设施**，排查范围小一半。

### 模块边界

```
src/
  github.ts    调 GitHub API，返回领域对象。不碰数据库
  db.ts        连接池 + upsert。不碰 HTTP
  service.ts   编排：fetchAndStore = fetchUser + upsertUser
  app.ts       Hono 路由、入参校验、错误 → 状态码映射
  local.ts     本地入口（@hono/node-server）
  lambda.ts    部署入口（hono/aws-lambda）
```

依赖方向单向：`local|lambda → app → service → {github, db}`。

`github.ts` 不知道数据库存在，`db.ts` 不知道 GitHub 存在。**`local.ts` 和 `lambda.ts` 加起来才 10 行**——业务逻辑一行不用改就能从本地搬到 Lambda。

### Lambda 特有：连接池必须在模块作用域

Lambda 执行完不会立刻销毁，而是「冻结」容器等待复用（热启动）。

```ts
// db.ts —— 模块顶层，冷启动时执行一次
let pool: pg.Pool | undefined;
export function getPool(): pg.Pool {
  pool ??= new pg.Pool({ connectionString: process.env.DATABASE_URL, max: 2 });
  return pool;
}
```

**如果把连接池建在 handler 函数内部**，每次请求都会新建连接，RDS 的连接数很快被打爆。

`max: 2` 而不是默认的 10——单个 Lambda 实例同一时刻只处理一个请求，连接开多了纯属浪费 RDS 配额。

### upsert 的唯一约束只加在 username

```sql
INSERT INTO github_users (username, github_id, ...)
VALUES ($1, $2, ...)
ON CONFLICT (username) DO UPDATE SET
  ..., updated_at = now()
RETURNING *
```

**不要给 `github_id` 也加唯一约束。** GitHub 用户可以改名，若两个字段都唯一，改名后 upsert 会同时命中两个冲突键，语义不确定。作业场景下单一冲突键最清晰。

`created_at` / `updated_at` 记录的是「我们抓取的时间」，与 `github_created_at`（对方注册时间）区分开。

### fetch 必须设超时

```ts
signal: AbortSignal.timeout(5000)
```

不加的话，GitHub 无响应时 Lambda 会一直挂到自己超时（15 秒），白白烧掉执行时间和钱。

### 错误分层

`github.ts` 抛出带类型的错误（`UserNotFoundError` / `RateLimitError` / `UpstreamError`），`app.ts` 在一处集中捕获并翻译成状态码。

**业务模块不需要知道 HTTP 是什么。**

| 情况 | 状态码 |
|------|--------|
| 请求体不是合法 JSON / username 格式非法 | `400` |
| GitHub 返回 404 | `404` |
| GitHub 返回 403 且 `x-ratelimit-remaining: 0` | `429` |
| GitHub 5xx 或超时 | `502` |
| 数据库写入失败 | `500` |

注意 403 的判断：GitHub 也会对被封禁的账号返回 403，所以要**同时检查限流头**才能确定是限流。

### fetch 的失败有两条路径

```ts
try {
  response = await fetch(url, { signal: AbortSignal.timeout(5000) });
} catch (cause) {
  // DNS 挂了、断网、CORS 预检被拒 —— fetch 抛异常，不返回 Response
  throw new UpstreamError(...);
}
if (!response.ok) {
  // HTTP 层面的失败 —— fetch 正常返回，只是 status >= 400
}
```

**网络层失败时 `fetch` 抛异常而非返回响应**，这两条路径必须都处理，否则断网时页面会白屏。

### CORS：错误响应上也必须有 CORS 头

如果 404 响应上没有 `Access-Control-Allow-Origin`，浏览器会把它显示成**含糊的 CORS 错误**，而不是真实的 404。前端永远没法告诉用户「这个 GitHub 用户不存在」。

Hono 的 `cors()` 中间件在 `onError` 之后仍能加上头，但**很多框架不是这样**（错误响应绕过中间件链）。这值得写个测试锁住：

```ts
it("sets the origin header on an error response too", async () => {
  vi.mocked(fetchAndStore).mockRejectedValue(new UserNotFoundError("nobody"));
  const res = await post({ username: "nobody" });
  expect(res.status).toBe(404);
  expect(res.headers.get("Access-Control-Allow-Origin")).toBe(ORIGIN);
});
```

### 前端状态用单一联合类型，不用三个布尔量

```ts
type State =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "success"; user: GitHubUser }
  | { status: "error"; message: string };
```

三个布尔量（`isLoading` / `hasError` / `hasData`）能组合出 8 种状态，其中 5 种非法（比如同时 loading 又 error）。迟早会因为忘记重置某个而出 bug——最典型的就是**旧的错误提示留在屏幕上，旁边却显示着新的成功结果**。

单一状态变量从类型上就杜绝了这种情况。测试要覆盖：

```ts
it("clears a previous error when a new search succeeds", ...)
it("clears a previous card when a new search fails", ...)
```

### null 不是边缘情况

大多数 GitHub 用户不填 `bio` 和 `company`。渲染时不判断就会在页面上**打印出字符串 "null"**。

```ts
it("omits optional fields instead of rendering null", () => {
  render(<UserCard user={{ ...base, bio: null, company: null }} />);
  expect(screen.queryByText("null")).not.toBeInTheDocument();
});
```

### 数据库层测试要连真库

```
db.test.ts  →  Docker 里的真实 PostgreSQL（不 mock）
```

`ON CONFLICT` 是 PostgreSQL 特有行为，**mock 掉就等于什么都没测**。

## 10. 部署：SAM

### 手动与自动化的分界线

| 层 | 谁管 | 为什么 |
|----|------|--------|
| VPC、子网、路由表、NAT、安全组、RDS、跳板机 | **手动** | 长期稳定、少变；亲手搭一遍收获最大 |
| Lambda、API Gateway | **SAM** | 随代码频繁变更，手动重传 zip 很快就烦了 |

SAM 模板把手动建好的资源当**参数**传进去。这是很多真实团队的做法：网络基础设施长期稳定、单独管理；应用层高频变更、走 CI/CD。

### 坑：SAM 的 List 类型参数与 shell 转义

```yaml
# 别这么写
SubnetIds:
  Type: List<AWS::EC2::Subnet::Id>
```

命令行传值要转义逗号：`SubnetIds="subnet-a\,subnet-b"`。而 **zsh 在双引号里保留反斜杠**，`\,` 会原样传给 SAM，subnet ID 末尾多个 `\`：

```
Parameter validation failed: parameter value subnet-0002fe719ea8b06de\
for parameter name SubnetIds does not exist
```

**改用两个标量参数彻底绕开**：

```yaml
SubnetIdA:
  Type: AWS::EC2::Subnet::Id
SubnetIdB:
  Type: AWS::EC2::Subnet::Id
```

```yaml
VpcConfig:
  SubnetIds: [!Ref SubnetIdA, !Ref SubnetIdB]
```

### 顺带一提：zsh 不做变量分词

```bash
R="--region us-west-2"
aws ec2 describe-vpcs $R      # bash 可以，zsh 报 Unknown options
```

zsh 默认不对未加引号的变量做 word splitting。用环境变量代替：

```bash
export AWS_DEFAULT_REGION=us-west-2
aws ec2 describe-vpcs
```

### 坑：PowerUserAccess 不能创建 IAM 角色

SAM 要为 Lambda 创建执行角色，需要 `iam:CreateRole`。PowerUserAccess 禁止一切 IAM 写操作：

```
User: arn:aws:iam::089783390738:user/ai_user is not authorized
to perform: iam:CreateRole
```

**这不是配置错误，是 AWS 的有意设计**：能创建 IAM 角色 ≈ 能给自己提权（造一个 Administrator 角色然后扮演它）。

三条路：

| 方案 | 评价 |
|------|------|
| 手动建好执行角色，模板引用 | 不放大权限，最干净 |
| 给受限的内联策略（限定 `role/zuoye-*` 前缀） | 有边界，SAM 仍能自动建角色 |
| 附加 `IAMFullAccess` | 最省事，但访问密钥明文存在笔记本上 = 交出提权能力 |

本项目当时选了第三条，后来在第 11 章用 OIDC 彻底解决。

### 坑：ROLLBACK_FAILED 的清理

CreateRole 被拒后，CloudFormation 回滚时又需要 `iam:DeleteRolePolicy`——同样被拒，于是卡在 `ROLLBACK_FAILED`。

```bash
aws cloudformation delete-stack --stack-name zuoye-collector
# 变成 DELETE_FAILED
aws cloudformation delete-stack --stack-name zuoye-collector \
  --retain-resources CollectorFunctionRole
```

`--retain-resources` 让它跳过删不掉的资源。

> **正面意义**：CloudFormation 校验没过就**整体回滚**，没留下半成品。手动点控制台的话，你可能已经建好了 Lambda、卡在 API Gateway，然后得手工清理。这就是 IaC 值得用的地方。

### 坑：SAM CLI 的 cfn-lint

| 版本 | 现象 |
|------|------|
| 1.99.0 | `sam validate --lint` 报 `nodejs22.x` 不是有效运行时（规则库停在 nodejs18.x） |
| 1.163.0 | `sam validate --lint` 直接崩溃：`UnexpectedRuleException: cannot import name 'REGISTRY_SCHEMAS'` |

两个都是 **linter 自身的问题，不影响部署**。去掉 `--lint` 用基础校验即可：

```bash
sam validate --region us-east-2
```

### 打包策略

用 esbuild 打成**单文件**，不上传 `node_modules`：

```json
"build": "esbuild src/lambda.ts --bundle --sourcemap --platform=node --target=node22 --format=esm --outfile=dist/index.mjs --banner:js=\"import{createRequire}from'module';const require=createRequire(import.meta.url);\""
```

- `--format=esm` + `.mjs` 后缀：Lambda 的 Node 18+ 自动按 ESM 处理，handler 写 `index.handler`
- `--banner:js` 注入 `createRequire`：`pg` 内部有动态 `require`，ESM 环境下没有这个全局函数
- `--sourcemap`：配合 `NODE_OPTIONS: --enable-source-maps`，CloudWatch 里的堆栈才指向源码行号

**坑**：模板里设了 `--enable-source-maps` 但构建时不加 `--sourcemap`，这个选项形同虚设。本项目最初就是这样，后来才修。

### 数据库连接串：本地和云上不一样

| 环境 | host | port |
|------|------|------|
| 本地经隧道 | `localhost` | `5433` |
| Lambda 在 VPC 内 | `database-1.xxx.rds.amazonaws.com` | `5432` |

很多人第一次做会把本地的连接串直接贴到 Lambda，然后困惑为什么连不上。

本项目用两个 gitignored 文件区分：`.env.aws`（本地迁移）和 `.env.deploy`（Lambda）。后者由前者派生，不需要暴露密码：

```bash
sed 's|@localhost:5433|@database-1.xxx.rds.amazonaws.com:5432|' .env.aws > .env.deploy
```

## 11. CI/CD：GitHub Actions 与 OIDC

### OIDC 解决什么问题

传统做法：把 AWS 访问密钥存进 GitHub Secrets。**这是一个永不过期的长期凭证**，一旦泄露（日志打印、恶意 action、内部人员）后果严重。

OIDC 的思路完全不同：**CI 不持有任何长期密钥**。

1. GitHub 现场签发一个 OIDC 令牌（JWT），里面写明「我是 `repo:xxx/yyy` 的 `main` 分支」
2. CI 把这个令牌交给 AWS STS
3. AWS 验证签名，检查令牌内容是否匹配角色的信任策略
4. 匹配则发放**有效期 1 小时**的临时凭证

跑完就失效，没有任何东西可以泄露。

### 创建身份提供商

```bash
aws iam create-open-id-connect-provider \
  --url https://token.actions.githubusercontent.com \
  --client-id-list sts.amazonaws.com \
  --thumbprint-list 6938fd4d98bab03faadb97b34396831e3780aea1
```

一个 AWS 账号只需要建一次，所有仓库共用。

### 信任策略：整个 OIDC 配置的命门

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": {
      "Federated": "arn:aws:iam::089783390738:oidc-provider/token.actions.githubusercontent.com"
    },
    "Action": "sts:AssumeRoleWithWebIdentity",
    "Condition": {
      "StringEquals": {
        "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",
        "token.actions.githubusercontent.com:sub": "repo:jaredchao/github-user-collector:ref:refs/heads/main"
      }
    }
  }]
}
```

逐条解释：

| 条件 | 作用 |
|------|------|
| `Federated: .../token.actions.githubusercontent.com` | 只接受 GitHub Actions 签发的令牌 |
| `aud = sts.amazonaws.com` | 令牌必须是**专门签给 AWS STS** 的，不能拿别处签的来用 |
| `sub = repo:owner/repo:ref:refs/heads/main` | **只有这一个仓库的 main 分支**能扮演 |

**`sub` 这一条是命门。** 漏掉它、只写 `Federated` 和 `aud` 的话，**地球上任何一个 GitHub 仓库的 Actions 都能扮演你这个角色**。攻击者建个仓库、跑个 workflow 就进了你的 AWS 账号。这是 OIDC 配置最经典、后果最严重的错误。

**必须用 `StringEquals` 而非 `StringLike`**：

| 写法 | 谁能扮演 |
|------|---------|
| `StringEquals` + 完整 sub | 只有 `owner/repo` 的 `main` 分支 |
| `StringLike` + `repo:owner/*` | 你名下**任何仓库** |
| `StringLike` + `repo:*/repo-name:*` | **任何人 fork 你的仓库**都能拿到权限 |

其他常见的 `sub` 格式：

```
repo:OWNER/REPO:ref:refs/heads/BRANCH     # 特定分支
repo:OWNER/REPO:ref:refs/tags/TAG         # 特定 tag
repo:OWNER/REPO:environment:production    # 特定 environment（推荐用于生产）
repo:OWNER/REPO:pull_request              # PR 触发（谨慎，任何人都能提 PR）
```

### 角色权限：最小化

```bash
aws iam create-role --role-name zuoye-github-actions-deploy \
  --assume-role-policy-document file://trust-policy.json \
  --max-session-duration 3600

aws iam attach-role-policy --role-name zuoye-github-actions-deploy \
  --policy-arn arn:aws:iam::aws:policy/PowerUserAccess
```

再加一条内联策略，把 IAM 权限限定在本项目的前缀内：

```json
{
  "Effect": "Allow",
  "Action": [
    "iam:CreateRole", "iam:DeleteRole", "iam:GetRole", "iam:PassRole",
    "iam:TagRole", "iam:UntagRole",
    "iam:AttachRolePolicy", "iam:DetachRolePolicy",
    "iam:PutRolePolicy", "iam:DeleteRolePolicy", "iam:GetRolePolicy",
    "iam:ListRolePolicies", "iam:ListAttachedRolePolicies"
  ],
  "Resource": "arn:aws:iam::089783390738:role/zuoye-collector-*"
}
```

SAM 需要创建 Lambda 执行角色，但**不该能碰其他角色**。

### workflow 里必须声明 id-token 权限

```yaml
permissions:
  id-token: write     # 没有这行，GitHub 根本不签发令牌
  contents: read
```

**漏了它，`configure-aws-credentials` 会报一个含糊的 400 错误**，很难联想到是权限声明的问题。

### 完整的 workflow 骨架

```yaml
name: Deploy backend
on:
  push:
    branches: [main]
    paths: ["backend/**", ".github/workflows/backend.yml"]

permissions:
  id-token: write
  contents: read

jobs:
  test:
    runs-on: ubuntu-latest
    services:
      postgres:                    # db 层测试连真库
        image: postgres:16-alpine
        env: { POSTGRES_USER: appuser, POSTGRES_PASSWORD: localdevpassword, POSTGRES_DB: github_users }
        ports: ["5432:5432"]
        options: >-
          --health-cmd "pg_isready -U appuser -d github_users"
          --health-interval 3s --health-retries 10
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22, cache: npm, cache-dependency-path: backend/package-lock.json }
      - run: npm ci
      - run: npm run typecheck
      - run: npm test
      - run: npm run build

  deploy:
    needs: test
    if: github.event_name == 'push'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci && npm run build
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: ${{ secrets.AWS_DEPLOY_ROLE_ARN }}
          aws-region: us-east-2
      - uses: aws-actions/setup-sam@v2
        with: { use-installer: true }
      - run: sam deploy --stack-name zuoye-collector ... --no-confirm-changeset
      - name: Smoke test          # 部署后真的打一次线上 API
        run: |
          API=$(aws cloudformation describe-stacks --stack-name zuoye-collector \
            --query 'Stacks[0].Outputs[?OutputKey==`ApiUrl`].OutputValue' --output text)
          test "$(curl -s -o /dev/null -w '%{http_code}' "$API/health")" = "200"
```

### 坑：gh CLI 需要 workflow scope

推送包含 `.github/workflows/*.yml` 的提交时：

```
! [remote rejected] main -> main (refusing to allow an OAuth App to create or
  update workflow `.github/workflows/frontend.yml` without `workflow` scope)
```

```bash
gh auth refresh -h github.com -s workflow
```

这是 GitHub 的安全设计：**能写 workflow = 能在 CI 里跑任意代码、读取仓库所有 Secret**，所以单独设了一个 scope 卡住。

### 坑：CI 绿灯什么都不证明

第一次跑通时输出是：

```
No changes to deploy. Stack zuoye-collector is up to date
```

**代码和之前手动部署的一模一样，CloudFormation 没检测到差异。** 「CI 能真正发布新代码」这件事根本没被验证。

正确的验证方式是**对比部署前后的产物指纹**：

```bash
# 部署前
aws lambda get-function-configuration --function-name zuoye-collector \
  --query '{CodeSha256:CodeSha256,LastModified:LastModified}'
# CodeSha256: oXGDJgHo/upDczeTaireLUQG0cY3BkDFFPnUr8k5myE=

# 改一行代码，推送，等 CI 跑完

# 部署后
# CodeSha256: 3iKEE638STwsqEFhQLo5pzJ/W1TeRR46RFKsjw0156E=   ← 变了，说明真的部署了
```

前端同理，对比构建产物的哈希文件名：

```bash
curl -s https://zuoye-frontend.pages.dev | grep -oE '/assets/index-[^"]+\.js'
# /assets/index-1JlmwozI.js  →  /assets/index-DNsuSUGg.js
```

**验证要证伪，不能只求证。**

### 安全测试也要测反面

CORS 收紧后，只测「合法来源能用」是不够的——一个配错成 `*` 的白名单同样会显示「通过」。必须同时测「非法来源被拒」：

```bash
# 合法来源
curl -s -D - -X OPTIONS $API/users -H 'Origin: https://zuoye-frontend.pages.dev' \
  -H 'Access-Control-Request-Method: POST' | grep -i access-control-allow-origin
# access-control-allow-origin: https://zuoye-frontend.pages.dev

# 非法来源
curl -s -D - -X OPTIONS $API/users -H 'Origin: https://evil.example.com' \
  -H 'Access-Control-Request-Method: POST' | grep -i access-control-allow-origin
# (无输出) ← 正确
```

## 12. 前端与 Cloudflare Pages

### 两种部署方式

| 方式 | 做法 | 评价 |
|------|------|------|
| **A. Cloudflare Git 集成** | 网页控制台连 GitHub 仓库，自动拉代码构建 | 标准用法，但必须在浏览器里 OAuth，且构建过程是黑盒 |
| **B. GitHub Actions + wrangler** | CI 里构建，`wrangler pages deploy` 推上去 | 前后端 CI 统一，每一步可见 |

本项目选 B：作业重点是搞懂 CI/CD 链路，方式 A 把这部分藏起来了。

### 创建项目并首次部署

```bash
npx wrangler login                    # 浏览器 OAuth，无需贴密钥
npx wrangler whoami                   # 拿 Account ID
npx wrangler pages project create zuoye-frontend --production-branch=main
npm run build
npx wrangler pages deploy dist --project-name=zuoye-frontend --branch=main
```

`wrangler pages deploy` 在项目不存在时会交互式询问，**在 CI 里会失败**。所以要先 `project create`。

### API Token 的最小权限

CI 里的 wrangler 不能用 OAuth，需要 API Token。

Cloudflare 控制台 → 头像 → **My Profile** → **API Tokens** → **Create Token** → 拉到底 **Create Custom Token**：

- Permissions: `Account` → `Cloudflare Pages` → `Edit`
- Account Resources: Include → 你的账号

**不要用 Global API Key**——那是 Cloudflare 账号的万能钥匙。这个 token 常驻 GitHub Secrets，任何能改 workflow 的人都能读到。万一泄露，攻击者最多改你的 Pages 站点，动不了 DNS、域名、账单。

### 密钥不经过对话/日志的传递方式

```bash
# 用编辑器把 token 粘进一个 gitignored 文件，然后：
tr -d '\n\r \t' < .cf-token | gh secret set CLOUDFLARE_API_TOKEN
rm -f .cf-token
```

管道传递，不 `cat`、不 `echo`。同理，数据库连接串：

```bash
grep '^DATABASE_URL=' backend/.env.deploy | cut -d= -f2- | tr -d '\n' | gh secret set DATABASE_URL
```

### VITE_ 前缀的环境变量会被打进产物

```
frontend/.env.production
  VITE_API_URL=https://kp6eccqn9h.execute-api.us-east-2.amazonaws.com
```

这个文件**可以提交进仓库**——API 地址不是密钥，而且前端代码天然是公开的。

**绝不要把任何真正的秘密放进 `VITE_` 变量**，它会明文出现在打包后的 JS 里：

```bash
curl -s https://zuoye-frontend.pages.dev/assets/index-xxx.js | grep -oE 'https://[a-z0-9]+\.execute-api\.[a-z0-9-]+\.amazonaws\.com'
```

### 坑：vitest 2.x 与 Vite 6 的类型冲突

```
Type 'Plugin<any>' is not assignable to type 'PluginOption'.
  Type '.../node_modules/vite/...Plugin' is not assignable to
       '.../node_modules/vitest/node_modules/vite/...Plugin'
```

vitest 2.x 内部捆绑了 Vite 5 的类型。升级到 vitest 3 解决。

`vite.config.ts` 里要从 `vitest/config` 而非 `vite` 导入 `defineConfig`，否则 `test` 字段类型报错：

```ts
import { defineConfig } from "vitest/config";
```

### 坑：端口被占用时健康检查会假阳性

本地起服务时，3000 端口被机器上另一个 Next.js 应用占着，Hono 服务 `EADDRINUSE` 根本没起来。而健康检查 `curl localhost:3000/health` 打到了那个 Next 应用上，**返回了 200**。

**看到 200 就以为成功是不够的**，必须验证响应内容。后来把端口改成 3100。

## 14. 验证命令速查

### 网络

```bash
export AWS_DEFAULT_REGION=us-east-2

# VPC 的 DNS 开关
aws ec2 describe-vpc-attribute --vpc-id <vpc> --attribute enableDnsHostnames
aws ec2 describe-vpc-attribute --vpc-id <vpc> --attribute enableDnsSupport

# 子网与可用区分布
aws ec2 describe-subnets --filters "Name=vpc-id,Values=<vpc>" \
  --query 'Subnets[].[Tags[?Key==`Name`]|[0].Value,CidrBlock,AvailabilityZone,MapPublicIpOnLaunch]' --output table

# NAT 状态与公网 IP
```

### CloudMap 的两种形态（本项目全用上了）

Lambda 没有 IP、没有端口，**放不进 DNS 型命名空间的 A 记录**——而且 DNS_PRIVATE 命名空间强制要求 DnsConfig（实测 `InvalidInput` 报错）。所以 API 型注册必须住 HTTP 命名空间：

| | Lambda → Go（对内路） | Go → Lambda（搜索转发） |
|---|---|---|
| 命名空间 | `zuoye.internal`（DNS_PRIVATE） | `zuoye.api`（HTTP） |
| 注册的是什么 | 容器私网 IP（A 记录，TTL 10s） | 函数名/ARN（任意属性） |
| 怎么发现 | 普通 DNS 解析 | `DiscoverInstances` API |
| 怎么调用 | HTTP 直连 `go-service.zuoye.internal:8080` | AWS SDK `lambda:Invoke` |
| 谁维护注册 | ECS 服务自动注册/注销 | Lambda 栈的 CFN 资源自管 |

Go 调 Lambda 的细节：`DiscoverInstances` 结果缓存 30 秒；调用时构造 **API Gateway v2 格式的事件**（version/rawPath/requestContext.http/body），Lambda 侧 `hono/aws-lambda` 适配器无感，代码零改动；返回的 `{statusCode, body}` 原样透传，前端看到的状态码与走 API Gateway 完全一致。凭证来自任务角色 `zuoye-go-task-role`（`servicediscovery:DiscoverInstances` + `lambda:InvokeFunction`）。

## 17. 作业三：异步解耦、灰度发布与主动巡检

三个任务串成一条线：**采集改异步（任务 2）→ 用灰度方式发布这次改造（任务 3）→ 让巡检持续证明它还活着（任务 1）**，告警统一汇入一个 SNS 主题。

### 环境重建记录

作业二资源在 7-13 全量释放，本次从零重建：VPC/4 子网/IGW/NAT/路由表、5 个安全组、RDS、跳板机、OIDC 提供商与 5 个 IAM 角色、ECR+镜像、ECS 集群/服务、ALB+目标组+双监听器、ACM 通配符证书、CloudMap 双命名空间。

两个重建时才知道的事实：

- **Cloud Map 命名空间 ID 是账号+名称的确定性值**。删掉重建同名命名空间，拿到的 ID 与之前**完全相同**（`ns-5fkzrmwi3bzbrcx3` / `ns-m5syodpxwy3gzlo3`），所以 SAM 模板里写死的默认值不用改。验证方式是查它绑定的 Route53 私有区，确认指向新 VPC。
- **GitHub Actions 启用 workflow 有传播延迟**。`gh workflow enable` 之后立刻 push，那次 push 仍按禁用处理、不触发。而补推**空 commit 也不行**——`paths` 过滤匹配不到任何改动文件。最终给 workflow 加了 `workflow_dispatch` 手动入口，重建场景下专治这个。

### 任务 2：SNS → SQS → Worker，带死信队列

原来 `POST /users` 同步做完"调 GitHub + 写库"才返回，用户要等，且 GitHub 抖动直接变成用户可见的失败。改造后：

```
POST /users ──> SNS Topic ──> SQS 主队列 ──> Worker Lambda ──> GitHub + RDS
   │ 立即 202                    │ 重试 3 次仍失败
   │                             ▼
   └─ 调用方轮询 GET /users/:u   死信队列 ──> 深度 >0 告警 ──> AlertsTopic
```

**重试与死信的边界是这个设计里最需要想清楚的地方**。不是所有失败都值得重试：

| 失败 | 处理 | 为什么 |
|------|------|--------|
| GitHub 用户不存在（404） | 记日志，**当作已处理** | 重试三次它也不会存在，只会白占 DLQ 名额 |
| GitHub 限流 / 5xx / 超时 | 抛出，重试 | 典型的临时故障，等一会儿就好 |
| 数据库连接失败 | 抛出，重试 | 同上 |
| 消息体不是 JSON / 无合法 username | 抛出 → 进 DLQ | 真正的毒消息，需要人看 |

其他几个要点：

- **`ReportBatchItemFailures`**：一批 5 条消息里只有 1 条失败时，只把那 1 条报回去重试。不用这个的话整批重投，健康的 4 条会被重复采集（upsert 幂等所以不脏数据，但白白多打 4 次 GitHub API）。
- **`VisibilityTimeout` 必须大于函数超时**。设小了，SQS 会在第一个 worker 还在处理时把同一条消息交给第二个 worker。这里函数超时 15s、批量 5 条，取 120s。
- **幂等性是异步的前提**。SQS 是至少一次投递，重复消费必然发生；`ON CONFLICT (username) DO UPDATE` 让重复消费无害。
- **202 不是"成功"，是"已受理"**。前端因此改成"提交后轮询"：`POST` 拿 202，再轮询 `GET /users/:username` 直到 200（404 表示还在路上）。Go 前门同步加了一条 `GET /users/{username}` 转发路由供轮询。
- **投递失败必须回 500 而不是 202**。SNS 都没收到的请求，回 202 等于承诺一次永远不会发生的采集。

### 任务 3：灰度发布——从 CodeDeploy 退到别名加权路由

**本来的写法**是 SAM 两段配置：

```yaml
AutoPublishAlias: live
DeploymentPreference:
  Type: Canary10Percent5Minutes
  Alarms: [...]
```

**但这个账号用不了**。部署直接整栈回滚，根因藏在 `ServerlessDeploymentApplication` 的失败事件里：

```
The AWS Access Key Id needs a subscription for the service
(Service: CodeDeploy, Status Code: 400)
```

免费计划账号没有 CodeDeploy 订阅——和之前 CodeBuild 并发被锁 0 是同一类账号级限制。

**替代方案：自己驱动别名的加权路由。** 关键认识是 **CodeDeploy 并没有什么魔法**，它做的就是反复调用 `lambda update-alias` 调整 `AdditionalVersionWeights`，中间轮询告警。这个能力是 Lambda 别名原生的，不需要任何额外服务：

```bash
# 别名仍指向稳定版，只把一部分权重给候选版
aws lambda update-alias --function-name $FN --name live \
  --function-version $STABLE \
  --routing-config '{"AdditionalVersionWeights":{"'$TARGET'":0.1}}'
```

`scripts/canary-release.sh` 把整个流程写完整了：记录稳定版 → 发布前先确认告警不在 ALARM（否则陈年告警会让健康版本白白回滚）→ 切 10% → 轮询告警 5 分钟 → 无事则提升 100%，触发则一条 API 调用回滚。

一个设计细节：**别名始终指向稳定版，候选版只拿"额外权重"**。这样回滚就是"去掉权重"，永远不存在坏版本独占流量的瞬间。

告警也相应改了：不再用 `ExecutedVersion` 维度锁定单个版本（自建流程里版本号是脚本才知道的运行时值），而是盯 `live` 别名整体——灰度期间坏版本的错误会拉高别名的错误数，平时则兼作日常健康告警。时延告警用 p90 而不是均值，几个冷启动不该让一次正常发布回滚。

**最反直觉的一点：没有流量的灰度是无效的灰度。** 作业环境平时零流量，10% 的 0 请求还是 0，任何告警都不会触发，坏版本会一路"健康"地铺到 100%。所以演示回滚必须在灰度窗口内主动打流量制造样本（`scripts/canary-demo.sh` 干这个）。生产同理：低流量服务的灰度必须配合合成流量，否则那层保护是纸糊的。

### 任务 1：Synthetics 巡检

CloudWatch Synthetics canary，每小时跑一次，运行时选 **`syn-nodejs-5.2`**（纯 Node，不带浏览器，比 puppeteer/playwright 运行时更快更省；只有需要渲染页面时才用那两个）。

巡检步骤：Lambda API 健康 → Go 前门健康 → 投递采集 → 等 12 秒 → 回读断言 → 介绍接口。

**关键设计：回读不能只断言 200。** 采集是幂等 upsert，探测用户会一直留在库里；worker 就算彻底停摆，`GET /users/torvalds` 照样回 200，巡检照样全绿——这是一个会骗人的健康检查。所以脚本额外校验 `updatedAt` 的新鲜度（15 分钟内），只有异步链路真的跑通了，时间戳才会被刷新。

成本：每小时一次约 $1/月；每 5 分钟一次约 $10/月。作业用每小时，`CanaryIntervalMinutes` 参数可调。

### 作业三踩过的坑

| # | 坑 | 原因 | 解法 |
|---|-----|------|------|
| 1 | `gh workflow enable` 后立刻 push 不触发 | 启用状态有传播延迟 | 加 `workflow_dispatch` 手动入口 |
| 2 | 空 commit 也不触发 | `paths` 过滤匹配不到改动文件 | 同上，或改一个真实文件 |
| 3 | 重建后 CI 的 secrets 全部失效 | 子网/安全组/RDS 端点与密码全是新的 | `gh secret set` 更新 4 项 + DATABASE_URL |
| 4 | `tsc` 报 `string | undefined` | `noUncheckedIndexedAccess` 让索引访问带 undefined | 测试里用精确类型而非 `Record<string,string>` |
| 5 | 旧 CORS 测试断言 201 | 异步化后 POST 回 202，且不再经 service 层 | mock 换成 queue/db，断言改 202 |
| 6 | 冒烟测试断言 201 | 同上 | 改为"202 + 轮询至 200"，顺带覆盖整条异步链路 |
| 7 | 巡检可能假绿 | upsert 幂等，旧数据让 200 永远成立 | 断言 `updatedAt` 新鲜度 |
| 8 | 零流量下灰度形同虚设 | 10% 的 0 请求触发不了任何告警 | 灰度窗口内主动打流量 |

## 附：本项目的已知妥协

诚实列出比假装没问题得分高：

1. **数据库密码存于 Lambda 环境变量与 GitHub Secrets。** 前者在 AWS 控制台明文可见。正确做法是 Secrets Manager，由 Lambda 在运行时按 IAM 权限读取。因每密钥每月 $0.40 而未采用。

2. **连接串用 `sslmode=no-verify`。** 加密但不校验服务器证书。Lambda 在 VPC 内直连真实端点，主机名匹配，应改用 `verify-full` 并附 AWS RDS CA 证书包。

3. **本地 IAM 用户持有 `IAMFullAccess`。** 手动部署时 SAM 需要 `iam:CreateRole`。CI 已改用 OIDC 且权限受限，此授权可以摘除。

4. **单个 NAT Gateway，无跨 AZ 冗余。** 该 AZ 故障时两个私有子网都失去出网能力。生产环境应每 AZ 一个。

5. **RDS 单可用区。** 无自动故障转移。

6. **CI 冒烟测试会往生产库写数据。** 每次部署抓一次 `torvalds`。生产环境应指向独立的测试环境。

7. **PR 环境的镜像构建暂时不走 CodeBuild。** 新账号的 CodeBuild 并发被 AWS 隐性锁为 0（`StartBuild` 报 `Cannot have more than 0 builds in queue`，us-east-1/us-east-2 均拒，属账号级风控；Service Quotas 显示 10 但不生效）。提额工单 178383926300453 被拒，理由是"先积累至少一个账单周期的账号历史"。CodeBuild 项目、buildspec、IAM 角色均已建好备用，workflow 里 `USE_CODEBUILD` 开关切换；当前用 GitHub Actions buildx（QEMU 交叉构建 ARM64）顶替，下个账单周期后重新申请配额即可切回。
