# AWS 控制台导览

全部资源在 **us-east-2（俄亥俄）**，进控制台先确认右上角区域没选错。

最省事的入口是 CloudFormation：栈 **`zuoye-collector`** 的 **Resources** 标签页列出了这套东西的全部资源，点任意一行的物理 ID 就直接跳到对应服务的控制台。

https://us-east-2.console.aws.amazon.com/cloudformation/home?region=us-east-2#/stacks

## 任务 2：SNS / SQS / 死信队列

| 看什么 | 去哪 |
|---|---|
| 事件主题 | SNS → Topics → `zuoye-collector-ProfileEventsTopic-VcL9teI3KPTT` |
| 主队列 | SQS → `zuoye-collector-IntroductionQueue-KM0Lm9SevnWs` |
| 死信队列 | SQS → `zuoye-collector-IntroductionDeadLetterQueue-iv9ELVS8Lp2N` |
| 消费者 | Lambda → `zuoye-collector-IntroductionWorkerFunction-jJt1hqYvWMHO` |
| 告警 | CloudWatch → Alarms → `...DeadLetterQueueAlarm...` 与 `...QueueBacklogAlarm...` |

**主队列页面上值得看的三处**：

1. **Details → Dead-letter queue**：写着 `Maximum receives: 5` 和目标 DLQ——重试与死信的策略就在这里。
2. **Details → Visibility timeout: 3 minutes**：必须大于 Worker 的 30 秒超时，否则同一条消息会被两个 Worker 同时处理。
3. **Lambda triggers**：挂着 Worker 函数，`Report batch item failures` 是开的——一批消息里只有坏的那条会重试。

**SNS 主题页面** → Subscriptions：能看到它订阅到主队列，`Raw message delivery: true`（否则 Worker 还得拆一层 SNS 信封）。

**看一次真实的消息流转**：先在网页上搜一个没搜过的用户，然后进 Worker 函数 → **Monitor → View CloudWatch logs**，最新日志流里会有 `introduction generated for <用户名> (event ...)`。

**手动制造一条死信**（约 15 分钟）：主队列 → 右上角 **Send and receive messages** → 消息体填 `not-a-json-event` → Send。之后每 3 分钟 Worker 重试一次，第 6 次判定超限进 DLQ，DLQ 深度告警随即变红。看完记得在 DLQ 页面 **Purge** 清掉。

## 任务 3：灰度发布

Lambda → **`zuoye-collector-CollectorFunction-LkCAQ8KWoT3k`**

| 看什么 | 位置 |
|---|---|
| 版本列表 | **Versions** 标签页（目前 1、2、3） |
| `live` 别名 | **Aliases** 标签页 → 点 `live`，当前指向版本 3 |
| 灰度权重 | 进 `live` 别名 → **Edit** → 底部 **Weighted alias**，就是脚本操作的那个东西 |
| 回滚门禁 | CloudWatch → Alarms → `zuoye-collector-release-errors` / `-release-latency` |

**证明流量走的是别名而不是 `$LATEST`**：API Gateway → APIs → `zuoye-collector` → Routes → 任一路由 → Integration，目标 ARN 结尾是 **`:live`**。这一点很关键——如果这里指向函数本身，别名和灰度就全是摆设。

**在控制台亲手灰度一次**：`live` 别名 → Edit → Weighted alias 选另一个版本、权重填 10% → Save。改完在 CloudWatch 里就能看到两个版本各自的调用量。看完把权重删掉即可。

## 任务 1：Synthetics 巡检

CloudWatch → **Application Signals → Synthetics Canaries**（旧版菜单在 CloudWatch → Synthetics）。

现在这里是空的——canary 底层 Lambda 最低要 960MB，而本账号 Lambda 内存上限被锁在 512MB。配额工单 **178548747100968** 批准后，用 `EnableSyntheticsCanary=true` 重新部署即可出现。

巡检要探的目标现在就能看：浏览器打开 `<API 地址>/ready`，返回 `{"status":"ready"}` 表示 API Gateway → Lambda → Go on ECS → PostgreSQL 整条链路通着。

## 其他值得一看的

| 内容 | 位置 |
|---|---|
| Go 服务容器 | ECS → Clusters → `zuoye-cluster` → Services，Tasks 里能看到运行中的容器与其私网 IP |
| 负载均衡与分流 | EC2 → Load Balancers → `zuoye-alb` → Listeners → HTTPS:443 的规则（host 头分流） |
| 服务发现 | Cloud Map → Namespaces → `zuoye.internal`（DNS 型，Go 容器）与 `zuoye.api`（HTTP 型，Lambda） |
| 数据库 | RDS → Databases → `database-1`（私有子网，无公网访问） |
| 全部日志 | CloudWatch → Log groups，前缀 `/aws/lambda/zuoye-collector-*` 与 `/ecs/zuoye-go-service` |

## 费用

Billing and Cost Management → **Cost Explorer**，按服务分组看。目前的大头是 NAT Gateway、RDS、Fargate 和 ALB，合计约 $55/月；SNS/SQS/Lambda 在这个调用量下基本为零。
